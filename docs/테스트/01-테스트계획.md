## 1. 전략

이 제품의 버그는 **화면이 깨지는 방식이 아니라 숫자가 조용히 틀리는 방식**으로 온다.
사용자는 통계가 3% 틀린 걸 알아채지 못하고, 알아챈 순간 앱을 지운다.

그래서 테스트 비중을 이렇게 둔다.

| 대상 | 비중 | 이유 |
|---|---|---|
| **예산 계산기 (구간 병합)** | 최상 | 등록 검증과 통계가 같이 쓴다. 틀리면 두 화면이 동시에 틀린다 |
| **이관 트랜잭션 (멱등)** | 최상 | 실패하면 기록 유실 또는 이중 집계 |
| 배치 (자정 정산 · 주간 마감) | 상 | 시간 경계. 사람이 안 볼 때 돈다 |
| 캘린더 필터 | 상 | 하나만 새도 통계가 즉시 망가진다 |
| 화면 렌더 | 중 | 눈에 보이는 버그는 빨리 잡힌다 |

**`Clock`을 빈으로 주입해 시간을 고정한다.** 안 하면 자정·마감 경계 테스트를 아예 쓸 수 없다.

## 2. 예산 계산기 (T-02) ⭐

### 2.1 구간 병합 — 경계값

| # | 입력 | 기대 |
|---|---|---|
| 1 | 겹침 없음 `10-11`, `13-14` | 120분 |
| 2 | 완전 포함 `14-16`, `14-15` | 120분 (180 아님) |
| 3 | 부분 겹침 `10-11:30`, `10:30-11` | 90분 |
| 4 | **경계 접함** `10-11`, `11-12` | 120분 — 병합되지만 중복 계산 없음 |
| 5 | 3중 겹침 `14-16`, `14-15`, `14:30-15:30` | 120분 |
| 6 | 동일 구간 2개 | 1개분 |
| 7 | 0분 구간 | 무시 |
| 8 | 정렬 안 된 입력 | 정렬 후 병합해 결과 동일 |

> **#4가 핵심이다.** `[10,11)` 과 `[11,12)` 는 겹치지 않는다. `<=` 로 짜면 1분이 사라지거나 중복된다.
> 구간은 **반열린 구간 `[시작, 끝)`** 으로 통일한다.

### 2.2 24시간 캡

**판정 기준은 후보 블록의 "그날 몫 길이" vs 남은 시간이다** (N-026). 겹침을 뺀 증가분이 아니다.

| # | 상황 | 기대 |
|---|---|---|
| 9 | 점유 1380분(남은 60) + **90분** 블록 생성 | `BUDGET_EXCEEDED` |
| 10 | 점유 1380분(남은 60) + **60분** 블록 생성 | 성공 — **남은 시간과 같으면 통과** |
| 11 | 캘린더 20시간(겹침 7시간) → 실점유 13시간 | 11시간 남음. **생성 가능해야 한다** |
| 12 | 예산이 남은 상태에서 겹치는 자리에 블록 생성 | 성공 (규칙 1 — 배치는 자유) |
| 12-b | **점유 1440(남은 0)** 에서 겹치는 자리에 블록 생성 | `BUDGET_EXCEEDED` — 겹쳐도 길이만큼 쓴다 |
| 12-c | 자정을 넘는 23:00–01:00 블록, 남은 60분 | 성공 — **그날 몫 60분만 청구** |
| 12-d | 거부 시 응답 | `detail.occupiedBy` 에 점유 내역 포함 (정책 §2.4) |

> **#11이 규칙 2(합집합)의 존재 이유다.** 단순 합산이면 여기서 사용자가 앱에서 차단된다.
> **#12-b 가 규칙 3의 존재 이유다.** 증가분으로 세면 상한이 영원히 발화하지 않는다.
>
> ⚠️ 이전 판(#9 = 1380+60 → EXCEEDED, #10 = 1380+30 → "정확히 1440")은 **산술이 모순이었다.**
> 경계 원칙으로 다시 썼다 — **남은 시간과 같으면 통과, 1분이라도 넘으면 거부.** (N-026)

### 2.3 자정 경계

| # | 상황 | 기대 |
|---|---|---|
| 13 | `23:00–01:00` 블록 | 예산은 18일 60분 / 19일 60분 **분할 청구** |
| 14 | 같은 블록의 통계 귀속 | `stat_date` = **18일** (시작한 날) |

13과 14가 서로 다른 게 정상이다 (정책 2.3).

## 6. 타임존 (T-03) ⭐

**CI를 `TZ=UTC`로 돌린다.** 그게 Vercel 함수와 GitHub Actions 크론의 실제 환경이다.

| # | 상황 | 기대 |
|---|---|---|
| 39 | **`TZ=UTC`로 전체 스위트 실행** | **전부 통과해야 한다** — 코드가 존을 알고 있음을 증명한다 |
| 39-b | `TZ=Asia/Seoul` · `TZ=America/New_York` 로도 실행 | 결과가 39와 **완전히 동일해야 한다** |
| 40 | `23:59`(KST) 생성 블록의 `workDate` | 당일 |
| 41 | `00:01`(KST) 생성 블록의 `workDate` | 익일 |
| 42 | 마감 배치를 월요일 03:59 / 04:01(KST)에 실행 | 전자는 미실행, 후자는 실행 |
| 43 | `DateTime.fromISO('2026-08-19')`를 존 없이 파싱한 코드 | **ESLint가 막는다** (`no-restricted-syntax`) |

> #39와 #39-b가 이 절의 핵심이다. **환경을 세 개로 바꿔도 답이 같아야** 존이 코드에 박혀 있다는 뜻이다.
> 예전(EC2 전제)에는 *"UTC로 띄우면 실패해야 한다"* 였다 — 프로세스 TZ 고정에 기대던 시절의 테스트다.
> 서버리스로 오면서 **기대가 뒤집혔고, 더 강해졌다** (N-022).

### N-003 · 구글 캘린더는 "단방향 파이프 두 개"로 설계
📅 2026-08-18 · 개발

구글 캘린더 API는 읽기·쓰기 모두 가능하지만, 하나의 양방향 동기화로 만들면 **에코 루프**에 빠진다. 우리가 쓴 일정을 다시 읽어 통계에 이중 반영되고 24시간 예산도 우리가 쓴 것 때문에 우리가 잠긴다.

- 읽기: 구글 → NFS (열린 주만, 마감되면 중단)
- 쓰기: NFS → 구글 (완료 블록만, 옵트인)
- 차단막: `extendedProperties.private`에 NFS 블록 ID를 심고, 읽을 때 건너뜀

**버린 것:** 단일 양방향 동기화

### N-004 · 주간 마감 후 캘린더 재조회 금지
📅 2026-08-18 · 기획

**예외 1건:** 가입 시 최근 4~8주 백필 (빈 화면 이탈 방지)
**마감 시각:** 월요일 04:00 (일요일 밤 작업자에게 유예)

### N-007 · 가변 작업 영역과 불변 원장을 물리적으로 분리
📅 2026-08-18 · 개발

`ActiveBlock`·`ImportedCalendarEvent`(가변, 잦은 CUD)와 `TimeLog`(불변, append-only, 읽기 전용)를 다른 테이블로 둔다. 사실상 **CQRS의 가장 가벼운 형태**다.

- 통계용 복합 인덱스가 UPDATE 비용을 물지 않는다
- 통계 쿼리에 `where status='COMPLETED'` 가 영원히 따라붙는 일이 없다 — *존재 자체가 확정의 증거*
- 진행 중에만 의미 있는 컬럼과 완료 후에만 의미 있는 컬럼이 서로를 오염시키지 않는다

**대가:** 이관 트랜잭션이 새 실패 지점이 된다 → `(member_id, source_type, source_reference_key)` UNIQUE로 멱등성 확보

### N-020 · 스택 전환 — Java/Spring → **TypeScript 전면** ⭐⭐
📅 2026-08-18 · 개발 · 기획

**N-012(Java 17 + Spring Boot 3.2)를 폐기한다.**

사유: 회사 노트북이 **Java 11을 유지해야 한다.** Spring Boot 3.x는 JDK 17을 요구하고, Boot 2.7은 이미 OSS 지원 종료다. JDK를 못 바꾸는 상황에서 JVM 스택은 성립하지 않는다.

**로컬 환경 실측**
```
Node   v24.11.1   ✅   pnpm 10.23.0 ✅   MySQL 8.0.44 ✅
Docker / Go / .NET / Rust / JDK17     ❌
```
**설치가 0인 스택은 TypeScript + Node 하나뿐이었다.** 이 대화가 시작된 이유가 "설치를 못 한다"인데 그 제약을 유일하게 통과한다.

#### 확정 스택

| 층 | 선택 | 대체된 것 |
|---|---|---|
| 언어 | **TypeScript** | Java 17 |
| 백엔드 | **NestJS** | Spring Boot |
| ORM | **Prisma** | JPA + QueryDSL |
| 마이그레이션 | **Prisma Migrate** | Flyway |
| 프론트 | **Next.js (App Router)** | JSP + jQuery |
| 배치 | **NestJS standalone worker** | `@Scheduled` |
| 테스트 | **Vitest** | JUnit |
| DB | **MySQL 8** (변경 없음) | — |
| 패키지 | **pnpm workspace 모노레포** | Gradle |

#### 이 선택의 근거

1. **사용자가 이미 TypeScript로 프로젝트를 완성했다.** `cal_bak`은 9,000줄 규모의 TS 프로젝트다. 새 언어 학습이 아니라 쓰던 것을 쓰는 것이다.
2. **NestJS는 Spring Boot와 개념이 1:1로 대응한다.** `@Injectable`/`@Controller`/생성자 주입/`@Module`/`@Cron`. 설계한 아키텍처가 이름만 바뀌어 옮겨간다.
3. **Prisma는 QueryDSL과 같은 철학이다.** 스키마에서 타입을 생성한다.
4. ⭐ **예산 계산기를 서버와 클라이언트가 같은 코드로 쓴다.** 이 프로젝트 최대 위험으로 꼽았던 *"계산기가 두 벌이면 두 화면 숫자가 어긋난다"* 가 `packages/domain` 공유로 **구조적으로 제거된다.**

#### 버린 것 (정직하게)

- **`java.time`.** JS `Date`에는 `LocalDate`/`LocalDateTime` 구분이 없다. 자정 경계·주간 마감이 핵심 도메인인 이 프로젝트에서 이건 실질적 손실이다.
  → 대응: raw `Date` 산술 **금지**, Luxon만 사용, `TZ=Asia/Seoul` 프로세스 고정, 타임존 테스트 4건(T-03) 강화
- **멀티스레드.** Node는 싱글 스레드라 배치가 API를 막는다.
  → 대응: `apps/worker` 별도 프로세스로 분리. 배치는 반드시 1개만 돌아야 하므로 오히려 배포 구성이 제약을 표현하게 된다
- **JSP + jQuery** (원래 요구사항). JVM이 사라지면서 함께 사라진다.

### N-021 · 프론트엔드는 Next.js (App Router)
📅 2026-08-18 · 디자인 · 개발

세 가지 안(서버 템플릿+바닐라 TS / Next.js+NestJS / Next.js 단독) 중 **Next.js + NestJS 분리**를 채택.

**대가를 알고 고른다:** 확정 시안 A/B/C는 바닐라 HTML+CSS라 서버 템플릿이면 거의 복붙이었지만, **React JSX로 재작성**해야 한다. `cal_bak`이 프레임워크 없는 TS였으므로 React는 새로 배우는 부분이다.

**그럼에도 채택한 이유:** 생태계·자료·채용에서 표준이고, 팀 확장 여지가 있다. 학습 비용은 1회지만 표준의 이득은 프로젝트 내내 누적된다.

#### 프로세스 구성

```
apps/web     Next.js      화면 (3000)
apps/api     NestJS       REST API + 구글 OAuth (3001)
apps/worker  NestJS       배치 전용 (자정 정산 · 주간 마감)
packages/domain           ⭐ 예산 계산기 · 시간 유틸 (순수 함수)
packages/db               Prisma schema + client
```

**인증은 `apps/api`가 소유한다** (Auth.js를 web에 두지 않는다).
구글 **리프레시 토큰을 서버가 갖고 있어야 `worker`가 캘린더를 동기화**할 수 있기 때문이다. 토큰이 web 세션에만 있으면 배치가 캘린더를 읽지 못한다.
세션은 httpOnly 쿠키, EC2에서 nginx가 `/api` → api, 나머지 → web으로 리버스 프록시.

### N-022 · 인프라 — Supabase + Vercel 무료 티어 ⭐⭐
📅 2026-08-19 · 개발 · 인프라

**N-015(MySQL 8)와 N-020의 "EC2 배포"를 폐기한다.**

사용자 요구: *"supabase, vercel 무료버전으로 일단 배포해서 테스트할꺼야."*

| 항목 | 새 결정 | 폐기 |
|---|---|---|
| DB | **Supabase (PostgreSQL 15)** | MySQL 8 (N-015) |
| 호스팅 | **Vercel Hobby** | AWS EC2 |
| 배치 | **GitHub Actions 크론 → 보호된 HTTP 엔드포인트** | `apps/worker` 상주 프로세스 |

#### 이 결정이 깨뜨린 것 세 가지

**1. MySQL → PostgreSQL.** Prisma라 `provider` 한 줄이지만 raw SQL은 방언이 다르다.
`DATE_FORMAT(d,'%Y-%m')` → `to_char(d,'YYYY-MM')`. 스키마·제약·인덱스는 그대로 유효하다.
오히려 Postgres는 네이티브 `enum`이 있어 태그·상태 컬럼이 더 정확해진다.

**2. ⛔ `apps/worker`가 죽는다. — 가장 큰 손실.**
Vercel은 서버리스라 **상주 프로세스가 없다.** `@nestjs/schedule`의 `@Cron`은 영원히 실행되지 않는다.
자정 정산과 주간 마감은 이 제품의 핵심이므로 **배치를 밖에서 밀어 넣는 구조로 뒤집는다.**

**3. `TZ=Asia/Seoul` 고정이 불가능해진다.**
Vercel 함수는 UTC로 돈다. N-020에서 세운 "프로세스 TZ 고정" 방어선이 사라진다.
→ **대응이 오히려 더 강해졌다:** 프로세스 TZ에 *기대지 않고*, `packages/domain/time`이
모든 Luxon 호출에 `zone: 'Asia/Seoul'`을 명시하는 **유일한 출구**가 된다.
환경에 의존하던 방어를 코드로 끌어내린 셈이라, EC2로 옮겨가도 이 코드는 그대로 옳다.

#### 배치 — GitHub Actions 크론

세 안(Vercel Cron / GitHub Actions / Supabase pg_cron) 중 **GitHub Actions**를 채택.

| 안 | 왜 안 골랐나 |
|---|---|
| Vercel Cron | Hobby는 개수·빈도 제한이 있고 **실행 시각이 정확하지 않다.** "월요일 04:00"이 의미를 갖는 주간 마감에 부적합 |
| Supabase `pg_cron` | DB 안에서 도는데 정산 로직은 앱에 있다. `pg_net`으로 HTTP를 쏘는 우회가 필요해 층이 하나 더 는다 |
| **GitHub Actions** ✅ | 무료 · 개수 제한 없음 · 분 단위 정확 · 워크플로가 리포에 커밋되어 **이력이 남는다** |

```yaml
# .github/workflows/daily-settlement.yml
on:
  schedule:
    - cron: '5 15 * * *'   # UTC 15:05 = KST 00:05  ⭐ Actions 크론은 UTC 고정이다
```

⚠️ **시차 환산을 주석으로 남기는 곳을 한 군데로 가둔다.** 이 프로젝트가 반복해서 밟는 함정이
인프라 레벨에서 다시 나타난 것이므로, 크론 표현식 옆에 KST 환산을 반드시 병기한다.

**보호:** 엔드포인트는 `x-cron-secret` 헤더로만 열린다. 공개 URL에 정산 트리거가 노출되면
누구나 남의 원장을 정산시킬 수 있다. 시크릿 불일치 시 **404**를 반환한다(401이 아니라 —
존재 자체를 알리지 않는다).

**부수 효과:** Supabase 무료 프로젝트는 일정 기간 비활성이면 일시정지된다.
매일 도는 크론이 이걸 자연히 막아준다.

#### Prisma × 서버리스 — 커넥션 고갈 ⭐

함수 호출마다 커넥션을 새로 잡으면 Postgres 한도에 금방 닿는다. **잘 돌다가 갑자기 터진다.**

```
DATABASE_URL = postgresql://…@…pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=1
DIRECT_URL   = postgresql://…@…supabase.com:5432/postgres
```

- 런타임은 **풀러(6543)**, 마이그레이션은 **직결(5432)**. Prisma `datasource`에 `directUrl`로 분리 선언
- `connection_limit=1` — 함수 인스턴스 하나가 커넥션 하나만 쥔다
- `PrismaClient`는 **모듈 스코프 싱글턴**. 핸들러 안에서 `new` 하면 호출마다 커넥션이 는다

#### 이건 "테스트 배포" 결정이다

무료 티어의 제약(함수 실행시간 상한, 콜드스타트, 프로젝트 일시정지)은 검증 단계에선 받아들일 만하지만
사용자가 늘면 다시 볼 항목이다. **다만 Postgres 전환과 배치 외부화는 되돌리지 않는다** —
둘 다 EC2로 옮겨가도 그대로 유효하고, 오히려 더 이식성이 높다.

### N-023 · NestJS 폐기 — Next.js 단일 앱 (Route Handlers)
📅 2026-08-19 · 개발

**N-020·N-021의 `apps/api`(NestJS) / `apps/worker` 3프로세스 구성을 폐기한다.**

Vercel 서버리스 위에서는 NestJS의 이점 대부분이 사라진다.
요청마다 Nest 부트스트랩이 돌아 콜드스타트가 길어지고, 상주 프로세스가 없으니 `@Cron`도 못 쓴다.
**남는 건 데코레이터 문법뿐인데, 그 대가로 배포 복잡도를 전부 떠안게 된다.**

```
apps/web/src/app/
├── (screens)/…                     화면 (Server Component)
└── api/
    ├── blocks/route.ts             POST 생성 · GET 목록
    ├── blocks/[id]/pause/route.ts  상태 전이
    ├── day/route.ts                하루 예산 + 블록 + 일정
    ├── statistics/…/route.ts       통계
    ├── auth/google/…/route.ts      ⭐ OAuth (리프레시 토큰은 서버에서만)
    └── jobs/
        ├── daily-settlement/route.ts   ⭐ GitHub Actions 가 호출
        └── weekly-closing/route.ts

packages/domain    ⭐⭐ 그대로 유지 — 이 전환의 영향을 받지 않는다
packages/db        Prisma schema + client
```

**N-021의 인증 근거는 유지된다.** 리프레시 토큰을 서버가 가져야 배치가 캘린더를 읽을 수 있다는 것이
`apps/api` 분리의 이유였는데, **토큰은 어차피 DB에 있다.** Route Handler도 서버에서 돌므로 조건을 만족한다.
프로세스를 나눌 이유가 사라진 것이지, 원칙이 틀렸던 게 아니다.

#### 잃은 것 (정직하게)

- **NestJS DI 컨테이너.** 서비스 조립을 손으로 한다 → `lib/services/` 에 팩토리 함수로 명시적 조립
- **`class-validator` 파이프 자동 적용.** → Route Handler 입구에서 **Zod** 스키마로 파싱. `packages/domain`의 타입과 한 벌로 묶는다
- **계층 강제.** 프레임워크가 막아주지 않으므로 규약으로 지킨다 (아키텍처 §3)

#### 얻은 것

- 배포 대상이 **1곳**. Vercel push 한 번으로 화면과 API가 같이 뜬다
- **동일 출처(same-origin)** — CORS 설정이 사라지고, 세션 쿠키가 그냥 붙는다. `credentials: 'include'`도 불필요
- Server Component에서 서비스 함수를 **HTTP 없이 직접 호출**할 수 있다. 첫 렌더에서 자기 자신에게 fetch 하지 않는다

### N-024 · 버전 고정과 Next 16 실측 정정 ⭐
📅 2026-08-19 · 개발

O-02 스캐폴딩을 실제로 돌려보고 **아키텍처 문서 v3.0의 오류 3건을 잡았다.**
문서를 기억으로 쓰면 안 되는 이유를 그대로 보여준 사례라 정정 내용을 남긴다.

#### 고정된 버전

| 패키지 | 버전 | 비고 |
|---|---|---|
| Next.js | **16.3.1** | Turbopack이 `dev`·`build` 기본값 |
| React | **19.2.8** | |
| Prisma | **7.9.1** | |
| TypeScript | **5.9.3** | ⚠️ 최신은 7.0.2(네이티브 포트)지만 **5 라인 유지** |
| Luxon / Zod / Vitest | 3.7.2 / 4.4.3 / 4.1.11 | |
| Node / pnpm | 24.11.1 / 10.23.0 | Next 16 최소 요구 Node 20.9 |

**TypeScript 7을 쓰지 않는 이유:** `eslint-config-next` 16.3.1이 TS 5를 전제로 붙어 있고,
`create-next-app`도 `^5`를 깐다. 컴파일러 메이저를 프레임워크보다 앞서 올릴 이유가 없다.
TS 7은 툴체인이 따라온 뒤에 본다.

#### 정정 1 — `export const runtime = 'nodejs'` 는 불필요하다

아키텍처 v3.0 §3.1에 *"Prisma는 Edge에서 못 도니 `runtime = 'nodejs'`를 명시한다"* 라고 썼는데,
**Next 16에서 `'nodejs'`가 기본값이고 Edge 런타임은 deprecated 다.**
동봉 문서(`node_modules/next/dist/docs`)가 *"`runtime` export를 제거하라"* 고 명시한다.
→ **핸들러에 쓰지 않는다.**

#### 정정 2 — 동적 렌더는 루트 레이아웃에서 한 번만

*"핸들러마다 `dynamic = 'force-dynamic'`"* 이라고 썼지만, 검증 중 **실제로 사고를 재현했다.**

```
Route (app)
┌ ○ /          ← nowInAppZone() 을 쓰는 화면이 Static 으로 프리렌더됐다
```

`await cookies()` 같은 Request-time API를 건드리기 전에는 Next가 정적으로 굳힌다.
**빌드 시점의 날짜가 박제된 HTML이 배포된다.** 시간이 제품인 앱에서 이건 치명적이다.

루트 레이아웃에 한 줄 넣자 전 라우트가 `ƒ (Dynamic)`으로 바뀌었다.
NFS는 **정적 프리렌더 대상 화면이 하나도 없으므로** 이게 옳은 위치다.
세션 쿠키를 읽으면 자동으로 동적이 되긴 하지만, 그건 *우연히 그렇게 되는* 방어라 의도를 적어둔다.

#### 정정 3 — Request-time API가 전부 비동기다 (Next 16 파괴적 변경)

Next 15에서 도입되고 **16에서 동기 접근이 완전히 제거**됐다.

```ts
const cookieStore = await cookies();        // ⚠️ await 필수
const { blockId } = await props.params;     // ⚠️ params 도 Promise 다
```

`cookies` · `headers` · `draftMode` · `params` · `searchParams` 전부 해당된다.
`withMember` 가드와 `app/focus/[blockId]/page.tsx` 설계에 직접 영향을 준다.

#### 부수 결정

- **Cache Components(`use cache`)는 MVP에서 켜지 않는다.** NFS 화면은 거의 전부 회원별 동적 데이터라 캐시할 대상이 없고, 새 캐싱 모델은 *"남의 통계가 보이는"* 사고 면적만 넓힌다
- **워크스페이스 패키지는 TS 소스를 직접 내보낸다** (`exports: "./src/index.ts"`) + `transpilePackages`. 빌드 단계를 없애 `packages/domain` 수정이 즉시 반영된다
  → 이때 내부 import에 `.js` 확장자를 쓰면 번들러가 해석하지 못한다. **확장자 없이 쓴다**
- **pnpm 10의 postinstall 차단**은 `onlyBuiltDependencies` 화이트리스트로 푼다. 전면 허용하지 않는 건 공급망 사고 면적을 좁히기 위해서다

#### 교훈

> 이 프로젝트의 스택은 전부 내 학습 시점 이후 메이저가 올라가 있었다.
> **문서를 기억으로 쓰면 틀린다.** Next 16이 `node_modules/next/dist/docs`에 자기 문서를 동봉하고
> *"이건 네가 아는 Next가 아니다"* 라고 경고하는 것도 같은 이유다.
> **앞으로 프레임워크 API를 문서에 적기 전에 동봉 문서를 먼저 읽는다.**

### N-025 · Prisma 7 실측 정정 — 설정이 스키마 밖으로 나갔다 ⭐
📅 2026-08-19 · 개발

O-03에서 Prisma 7.9.1을 실제로 돌려보니 **아키텍처 v3.0 §7의 `datasource` 예시가 통째로 틀렸다.**
N-024와 같은 종류의 사고이므로 같은 방식으로 정정한다.

#### 무엇이 바뀌었나

| 항목 | Prisma 5·6 (문서에 쓴 것) | **Prisma 7 (실제)** |
|---|---|---|
| generator | `prisma-client-js` | **`prisma-client`** + `output` 필수 |
| 생성물 | 컴파일된 JS | **TypeScript 소스** |
| DB URL | `datasource { url = env(...) }` | **`prisma.config.ts`** 의 `datasource.url` |
| `directUrl` | `datasource.directUrl` | ⛔ **없어졌다** |
| 섀도 DB | `shadowDatabaseUrl` in schema | `prisma.config.ts` 의 `datasource.shadowDatabaseUrl` |
| 런타임 커넥션 | 스키마의 url 사용 | **드라이버 어댑터를 앱이 직접 넘긴다** |
| `migrate dev` | generate 자동 실행 | **자동 실행 안 함.** 따로 부른다 |

```prisma
// Prisma 7 — datasource 에 url 이 없다
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}
datasource db {
  provider = "postgresql"
}
```

```ts
// 런타임은 어댑터로 커넥션을 받는다
new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })
```

#### `directUrl` 소멸이 오히려 설계를 선명하게 했다

Prisma 7에서 `prisma.config.ts` 의 `datasource` 는 **CLI 전용**이다 — migrate · db pull · studio 만 쓴다.
런타임은 앱이 어댑터로 직접 연결한다. 그래서 URL 이 자연스럽게 둘로 갈린다.

| 용도 | 값 | 어디서 읽나 |
|---|---|---|
| 마이그레이션 | `DIRECT_URL` (5432 직결) | `packages/db/prisma.config.ts` |
| 런타임 | `DATABASE_URL` (6543 풀러 + `connection_limit=1`) | `apps/web/src/server/prisma.ts` (O-04) |

예전에는 한 `datasource` 블록에 두 URL 을 밀어 넣고 Prisma 가 알아서 고르길 기대했다.
지금은 **누가 어떤 커넥션을 쓰는지가 파일 위치로 드러난다.**

#### 부수 결정

- **생성물(`packages/db/generated/`)은 커밋하지 않는다.** 스키마에서 다시 만들면 되는 산출물이고, 커밋하면 스키마와 어긋난 채 굳는다. 대신 루트 `postinstall` 이 `prisma generate` 를 돌려 클론 직후에도 타입이 맞는다
- **초기 마이그레이션 SQL 은 DB 없이 만들었다** — `prisma migrate diff --from-empty --to-schema … --script`. Q-011(Supabase 계정)이 없어도 O-03을 끝까지 마칠 수 있었다. 적용만 남는다
- **`DATETIME` → `timestamptz(0)`** 로 올린다. 문서의 MySQL `DATETIME` 은 존이 없었다. 운영이 UTC 인 지금 "절대 시각"임을 타입이 말해주는 편이 안전하다
- **enum 은 Postgres 네이티브로.** 단 `exclusion_reason` 만 `varchar` — 필터 사유는 운영하면서 늘어나는데, enum 이면 하나 추가할 때마다 마이그레이션이 필요하다

#### enum 정합성 테스트를 추가했다 (그리고 즉시 버그를 잡았다)

같은 값 목록이 `packages/domain/types` 와 `schema.prisma` 두 곳에 산다.
Postgres 네이티브 enum 이라 **어긋나면 운영의 INSERT 에서 처음 터진다.**

`apps/web/src/server/enum-parity.test.ts` 를 추가했더니 **첫 실행에서 실제 불일치를 잡았다** —
도메인 `COMPLETION_TYPES` 에 `CALENDAR_IMPORTED`(주간 마감 이관)가 빠져 있었다.
문서에도 스키마에도 있는 값인데 도메인만 4종이었다.

> 값 목록이 두 곳에 사는 걸 없앨 수는 없다(도메인은 DB 를 import 하면 안 되므로).
> **없앨 수 없는 중복은 테스트로 묶어둔다.**

#### DATE 컬럼 변환 규약 ⭐

`work_date` · `stat_date` · `week_start_date` 는 도메인에서 `'yyyy-MM-dd'` 문자열이지만
드라이버를 거치면 **JS `Date`** 가 된다. 여기가 하루 밀리는 자리다.

```
'2026-08-19' 를 한국 시간 0시로 만들면 → UTC 2026-08-18T15:00 → DATE 컬럼에서 8월 18일로 잘린다
```

**규약: DATE 컬럼은 "그 날짜의 UTC 자정"으로만 표현한다.** 타임존 변환을 하지 않는다 —
애초에 시각이 아니라 달력 위의 한 칸이기 때문이다.
`packages/domain/time/date-column.ts` 가 이 변환의 유일한 출구이며, 잘못된 방식까지 테스트로 박아뒀다.

### N-026 · 24시간 상한은 "블록 길이" 기준으로 건다 ⭐⭐
📅 2026-08-19 · 기획 · 개발

**정책 §2.1 규칙 3 의 판정 기준을 확정한다.** B-05 구현 중 정책의 구조적 구멍이 드러났다.

#### 발견 — 현재 규칙 4줄로는 상한이 영원히 발화하지 않는다

예산 계산기는 모든 점유자를 그날 `[0, 1440)` 으로 잘라 넣는다.
그래서 **합집합은 수학적으로 1440을 넘을 수 없다.** 몇 개를 넣든, 몇 겹으로 겹치든.

규칙 1(배치는 자유)과 규칙 2(합집합)가 규칙 3(1440 상한)을 **도달 불가능**하게 만든다 —
겹쳐 놓으면 증가분이 0이므로 무한히 등록할 수 있다.

정책 §2.5 가 *"24시간 캡은 실제로는 거의 걸리지 않는다"* 고 이미 인정했지만
'거의'가 아니라 **'절대'** 였고, 그러면 §2.4(초과 시 동작 — 점유 내역 제시, 통계 제외 토글)가
통째로 죽은 코드가 된다.

#### 결정 — 등록 검증은 **후보 블록의 길이**로 한다

| | |
|---|---|
| 채택 | `블록의 그날 몫 길이 ≤ remainingMinutes` |
| 폐기 | `겹침을 뺀 증가분 ≤ remainingMinutes` |

```
남은 240분 (캘린더가 20시간 점유)
  180분 블록   → ✅  180 ≤ 240
  이어서 120분 → ⛔ BUDGET_EXCEEDED (남은 60)
  겹치는 자리에 놓아도 예산은 길이만큼 쓴다
```

**근거**
1. **미터의 숫자와 행동이 일치한다.** 화면이 "남은 4시간"이라 말해놓고 5시간을 받으면 그 미터는 거짓말이다
2. **사용자의 원래 요구가 이것이다** — *"구글캘린더에 이미 20시간 일정이 있는데 우리 쪽에서 4시간 초과해서 등록할 수 없다"* (총량 모델)
3. **§2.4 화면이 살아난다.** 초과가 실제로 발생해야 "무엇이 자리를 차지하는지" 보여줄 일이 생긴다

**규칙 1은 유지된다.** 막는 것은 *위치*가 아니라 *총량*이다.
예산이 남아 있는 한 캘린더 일정과 겹치는 자리에도 얼마든지 놓을 수 있다.

**대가:** 하루가 꽉 차면 겹쳐 놓는 것도 막힌다. 받아들인다 —
그 상황에서 사용자에게 필요한 건 블록 하나 더가 아니라 §2.4 의 정리 안내다.

**#11(겹침 많은 사용자)은 그대로 성립한다.** 남은 시간을 **합집합으로 계산**하는 규칙 2는 바뀌지 않았다.
캘린더 20시간이 7시간 겹쳐 있으면 여전히 11시간이 남는다.

#### 표시는 여전히 합집합이다

계산기가 두 벌이 되는 것 아니냐는 우려가 있을 수 있어 분명히 해둔다.

| 무엇 | 기준 |
|---|---|
| 점유 · 남은 시간 · 태그별 통계 | **합집합** (규칙 2, 변경 없음) |
| 등록 가능 여부 | **후보 길이 vs 남은 시간** |

계산기는 하나다. 상한 판정만 그 결과 위에서 한 번 더 비교한다 (`assertBlockFitsInBudget`).

#### 문서 정정

- **테스트계획 §2.2 #9·#10 의 산술이 맞지 않았다.**
  *"점유 1380 + 60분 → EXCEEDED"* 와 *"점유 1380 + 30분 → 성공(정확히 1440)"* 은 서로 모순이다
  (1380+60=1440 인데 앞은 초과, 뒤는 1410 인데 "정확히 1440").
  → **경계 원칙으로 다시 쓴다: 남은 시간과 같으면 통과, 1분이라도 넘으면 거부.**
- 정책 §2.1 규칙 3 에 판정 기준을 명시한다
- 정책 §2.5 의 *"거의 걸리지 않는다"* 는 유지한다. 이제는 사실이다 —
  겹침이 흔한 사용자는 합집합 덕에 여유가 남고, 캡은 진짜로 꽉 찬 날에만 걸린다

### N-027 · 집중 시간은 기록 구간의 길이를 넘을 수 없다
📅 2026-08-19 · 개발 · QA

B-04 정산 테스트를 쓰다 **자동 정산이 통계를 부풀리는 버그**를 찾았다.

#### 재현

```
22:00  사용자가 60분 블록을 시작하고 노트북을 덮은 채 잠들었다
00:05  자정 배치가 RUNNING 인 블록을 정산한다

  종료 시각 : 23:00  (계획 종료로 캡 — 이건 이미 맞게 돼 있었다)
  집중 시간 : 125분  ← 누적 + (now − lastResumed) 를 그대로 썼다
```

**60분짜리 블록에 2시간 넘는 집중이 원장에 박힌다.**
구간은 60분인데 집중만 125분이라 *"집중 시간 > 그 시간에 실재한 구간"* 이라는 모순이 남는다.

#### 왜 위험한가

원장은 **한 번 들어가면 UPDATE 하지 않는다.** 잘못된 값이 영원히 남는다.
게다가 이 경로는 드물지 않다 — 밤에 블록을 켜두고 잠드는 건 타이머 앱의 일상적인 사용 패턴이다.
자동 정산분이 통계를 부풀리는 가장 흔한 경로가 여기다.

#### 결정

**불변식을 코드로 강제한다:** `actualFocusMinutes ≤ endTime − startTime`

집중 시간은 "그 블록이 실재한 구간" 안에서만 셀 수 있다.
넘으면 구간 길이로 자른다. 모든 방아쇠(USER_COMPLETE · USER_ABANDON · MIDNIGHT_BATCH)에서
불변식이 성립하는 것을 테스트로 고정했다.

> 이 값이 잘린 행은 `completionType = AUTO_SETTLED` 로 이미 구분돼 있다.
> 나중에 "자동 정산분 제외" 필터를 걸 수 있게 출처를 남겨둔 것이 여기서 값을 한다.

**교훈:** 종료 시각만 캡하고 집중 시간을 안 캡하면 두 값이 어긋난다.
**같은 사실을 두 컬럼에 적을 때는 둘의 관계를 불변식으로 적어둔다.**

### N-029 · Vercel 배포는 CLI 로 한다 (Git 연동은 보조)

첫 실배포에서 **원인 네 개가 겹쳐** 두 시간 가까이 헤맸다. 재발 방지를 위해 전부 기록한다.

#### 결정 — 배포는 `vercel --prod` 로 한다

```bash
npx vercel login          # 최초 1회 (기기 코드 인증)
npx vercel link --yes --project nfs-web
npx vercel --prod --yes
```

**Git 연동은 켜두되 신뢰하지 않는다.** 그쪽은 Preview 를 만들어 미리보기용으로 쓴다.

**근거**
1. **원인이 코드에 있는지 플랫폼에 있는지 즉시 갈린다.** CLI 는 커밋 작성자·저장소 연결·플랜 제약을 타지 않는다
2. **로그를 바로 볼 수 있다.** `vercel logs <url>` 한 줄로 `invalid_client` 를 찾았다. 대시보드를 헤매지 않아도 된다

- **환경변수는 UI 에서 손으로 넣지 않는다.** 붙여넣기 오류가 조용히 숨는다.

- 배포 후 **반드시 `/api/health` 를 확인한다.** 앱·DB·타임존을 한 번에 본다
- 실패하면 **추측하지 말고 `vercel logs` 부터 본다**

#### 교훈

> 로그를 못 보는 상태에서 가설을 하나씩 시험하면, 원인이 여러 개일 때 **영원히 수렴하지 않는다.**
> 관측 수단부터 확보한다. 이 경우 CLI 로그인이 그 수단이었고, 그걸 마지막에 한 것이 실수였다.

### N-030 · 정산 구간의 상한은 「실제 시작 + 계획 길이」다
📅 2026-08-19 · 개발 · QA

B-06 을 **실제 API 로 돌려보다** 원장에 음수가 박히는 걸 찾았다.

#### 재현

```
14:00 계획 60분 블록을 16:13 에 만들어 즉시 시작 → 즉시 완료
  → actualFocusMinutes: −74
```

`settledEndTimeOf` 가 종료 시각을 **계획 종료(15:00)** 로 캡했는데,
실제 시작(16:13)이 그보다 뒤였다. 상한이 시작보다 앞서니 **구간 길이가 음수**가 되고,
집중 시간이 그 음수 구간에 맞춰 잘렸다.

#### 왜 단위 테스트가 못 잡았나

**모든 테스트가 계획 시각과 실제 시작 시각을 같게 두고 있었다.**
`started(at('14:00'))` 처럼 헬퍼가 둘을 한 값으로 묶어버려, 둘이 다른 경우가 한 번도 만들어지지 않았다.

> 테스트 헬퍼가 편의를 위해 두 값을 묶으면, **그 둘이 어긋나는 경우를 영원히 테스트하지 않게 된다.**
> N-027(집중 시간 상한)도 같은 함수에서 나왔다. 이 함수는 두 번 틀렸다.

#### 결정

**상한을 `계획 종료`에서 `실제 시작 + 계획 길이`로 바꾼다.**

| 상황 | 계획 종료 기준 (폐기) | 실제 시작 + 길이 (채택) |
|---|---|---|
| 22:00 계획·시작, 00:05 배치 정산 | 23:00 ✅ | 23:00 ✅ |
| 14:00 계획, 16:13 시작, 16:43 완료 | **−74분** ⛔ | 30분 ✅ |
| 14:00 계획, 16:13 시작, 20:00 배치 | **음수** ⛔ | 17:13 에서 잘림 ✅ |

"계획한 길이보다 오래 기록되지 않는다"는 원래 의도가 이 정의로 더 정확히 표현된다.
자정 배치 방어(N-027)도 그대로 성립한다.

**클램프 순서도 뒤집었다.** 길이 상한을 먼저, "시작보다 이를 수 없다"를 마지막에 적용한다 —
후자가 최종 불변식이기 때문이다.

집중 분에도 `Math.max(0, …)` 를 한 겹 더 뒀다. 원장은 UPDATE 하지 않으므로
음수가 한 번 들어가면 통계 합계를 영원히 갉아먹는다.

#### 교훈

> **순수 함수 테스트만으로는 부족하다.** 이 버그는 서비스가 도메인에 넘기는 값의
> *조합*에서 나왔고, 그 조합은 실제 API 를 태워야 만들어졌다.
> ⭐⭐ 표시한 작업은 단위 테스트 후 **반드시 실경로로 한 번 태운다.**

### N-031 · 자정 정산 대상은 "어제"가 아니라 **"오늘 이전 전부"** 다 ⭐

**날짜**: 2026-08-20 · **역할**: 개발 (아키텍트) · **관련 작업**: O-07 · B-08

#### 문제

자정 정산을 순진하게 짜면 `workDate = 어제` 를 처리한다. 이 전제는 **크론이 반드시 돈다**는 가정 위에 서 있다.

GitHub Actions 크론은 정시를 보장하지 않는다. 러너가 붐비면 수십 분 밀리고,
**60일간 커밋이 없는 레포에서는 스케줄이 아예 비활성화된다.** 배포가 깨진 날, 시크릿을 갈아끼운 날도 있다.
하루라도 거르면 그날 블록은 `ActiveBlock` 에 **영원히** 남는다 — 그다음 배치는 어제만 보기 때문이다.

남은 블록은 조용히 죽지 않는다. 하루 화면의 예산을 계속 갉아먹고 통계에는 안 잡힌다.

#### 결정

**`workDate < 오늘(KST)` 인 블록을 전부 걷어간다.**

- 한 번 걸러도 다음 실행이 밀린 날까지 따라잡는다. 배치가 **자기 치유적**이 된다
- 오늘 것은 절대 건드리지 않는다 — 지금 돌고 있는 블록을 죽이는 일이다
- 손으로 `workflow_dispatch` 를 눌러도 안전하다. 낮 2시에 눌러도 오늘 블록은 살아 있다

#### 함께 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 대상 단위 | **(회원 × work_date) 쌍**, `groupBy` 로 뽑는다 | 서비스 `settleAllBlocksOfDate` 의 시그니처가 (회원, 날짜)다. 밀린 날이 여러 개면 쌍도 여러 개다 |
| 한 번에 처리할 상한 | **200 쌍** · 넘으면 `hasMore: true` | 함수 실행시간 60초. `take: 201` 로 뽑아 "더 있는가"를 한 질의로 판단한다 (count 를 따로 세면 두 질의 사이에 대상이 바뀐다) |
| 재호출 | **워크플로가 `hasMore` 가 false 가 될 때까지 다시 부른다** (상한 20회) | 배치가 멱등하므로 재호출이 안전하다 |
| 메서드 | **POST** (API명세 §6 그대로) | 원장을 바꾸는 호출이다. GET 으로 열면 프리페치·크롤러가 정산을 일으킬 수 있다 |
| 실패 격리 | 회원 단위 `try/catch` → `failedMemberIds`, 블록 단위는 서비스가 `failedBlockIds` | 한 명의 커넥션 오류가 나머지 전원의 정산을 막으면 안 된다 |
| 워크플로 종료 코드 | 실패 배열이 비어 있지 않으면 **빨간 실패** | 200 을 받았다고 성공이 아니다. 조용히 넘어가면 아무도 모른다 |

#### 실경로 검증 (N-030 의 교훈대로)

로컬 dev + 실 DB 로 태웠다. 어제 22:00 에 시작해 켜둔 채로 둔 60분 블록:

```
정산 결과   AUTO_SETTLED · 22:00~23:00 · 집중 60분 · statDate 2026-08-18(KST)
오늘 블록   그대로 남음 ✅
두 번째 호출 settledBlockCount 0 (멱등) ✅
시크릿 없음/틀림 → 404 ✅   ·   GET → 405 ✅
```

밤샘 블록이 125분으로 부풀지 않는다 — N-027·N-030 의 두 상한이 실제로 작동하는 걸 배치 경로에서 확인했다.

### N-032 · 주간 마감을 B-11(캘린더 동기화) 없이 먼저 만든다 ⭐

**날짜**: 2026-08-20 · **역할**: 개발 (아키텍트) · **관련 작업**: B-09 · O-07

#### 상황

정책 §3.2 의 마감 절차는 6단계다.

```
1. 지난주 구간 최종 1회 동기화      ← B-11 이 없다
2. 제외되지 않은 이벤트만 대상
3. 겹침 차감 → 0분이면 스킵
4. TimeLog INSERT (GOOGLE_CALENDAR)
5. 그 주 imported_calendar_event DELETE
6. weekly_closing = CLOSED
```

1번을 못 한다고 2~6번을 미루면 **`imported_calendar_event` 가 영원히 열린 채로 쌓인다.**
백필(B-13)은 선행이 B-09 라 그것도 같이 막힌다.

#### 결정

**2~6단계를 지금 만들고, 1단계는 `performFinalCalendarSync` 함수 하나로 자리만 잡아둔다.**

그 함수가 지금 하는 일은 연동 상태 판정뿐이다:

| 회원 상태 | `calendar_sync_result` | 이유 |
|---|---|---|
| 구글 미연동 | `NOT_CONNECTED` | 사실 그대로 |
| 연동돼 있는데 최종 동기화 못 함 | **`FAILED`** | 정책 §3.4 — *"조용히 0시간으로 처리하지 않는다"* |

⭐ **`SYNCED` 로 적지 않는 게 핵심이다.** 적으면 리포트가 "이 주는 캘린더가 반영됐다"고
거짓말을 하고, 사용자는 비어 있는 주를 보며 자기가 일을 안 했다고 착각한다.
`FAILED` 는 그 주 리포트에 *"이 주는 캘린더가 반영되지 않았습니다"* 를 띄우는 값이다 —
지금 상태를 정확히 설명한다.

#### 함께 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 마감 판정 | `weekStartDate < 이번 주` **그리고** `now >= 다음 월요일 04:00` | 마감은 되돌릴 수 없다(재개봉 없음). "지난주니까"가 아니라 **기한 초과**로 판단해야 배치가 밀려도 결과가 같다 |
| 대상 수집 | ① `weekly_closing` 이 `OPEN` 인 주 ② 마감 행 없이 일정만 남은 주 | ②가 없으면 동기화가 중간에 끊긴 주의 일정이 영원히 원장에 못 들어간다 |
| 여러 날 걸친 일정 | **날짜별로 예산 계산기를 돌려 더한다** | 계산기가 하루 단위인 건 한계가 아니라 정의다. 1440분 상한은 날짜별 규칙이다 |
| 원장 행 수 | 일정 하나에 **한 줄** (`statDate` = 시작한 날) | `UNIQUE(member, source_type, source_reference_key)` 가 날짜별 분할을 허용하지 않는다. 귀속 규칙도 블록과 같아야 통계가 안 갈린다 |
| `plannedMinutes` | 잡아둔 길이 | 캘린더에 "계획"이 따로 없다. 0 을 넣으면 달성률 화면이 0으로 나눈다 |
| 제외된 일정 | 원장에 안 넣고 **삭제는 한다** | 주가 동결되면 다시 볼 일이 없다 |
| 이미 CLOSED 인 주에 일정이 남아 있으면 | **지운다 + `console.warn`** | 원장에 들어갈 길이 없는데 예산 계산기는 계속 점유자로 센다. 하루가 조용히 좁아진다 |

#### 실경로 검증

로컬 dev + 실 DB. 지난주 일정 4건 + 앞선 주 1건 + 이번 주 1건을 심고 마감했다.

```
겹침 없는 60분          → 원장 60분
NFS 블록과 완전히 겹침  → 0분, 원장에 안 들어감 (실측 우선이 실제로 작동)
자정 넘는 120분         → 원장 120분, statDate = 시작한 날
필터 제외된 일정        → 원장 X, 삭제 O
마감 행 없던 앞선 주    → 같이 닫힘 (대상 수집 ②)
이번 주 일정            → 그대로 살아 있음
두 번째 호출            → closedWeekCount 0 (멱등)
동결된 주에 끼워 넣은 일정 → 정리됨, 원장 유입 없음
```

검증용 행은 전부 삭제했다.

### N-033 · 생성 시트의 미리보기 판정을 도메인으로 내린다 ⭐

**날짜**: 2026-08-20 · **역할**: 개발 (아키텍트) · **관련 작업**: D-04 · U-06

#### 문제

블록 생성 시트(S-05)는 칩을 누를 때마다 *"이 블록을 만들면 오늘 남은 시간 12시간 30분"* 을 갱신해야 한다.
두 가지 방법이 있었다.

| 안 | 문제 |
|---|---|
| 칩을 누를 때마다 서버에 물어본다 | 숫자가 늦게 따라온다. **미리보기의 의미가 사라진다** |
| 화면이 직접 계산한다 | 계산기가 두 벌이 된다 — 화면의 "남은 시간"과 서버 검증이 갈린다 |

두 번째의 위험이 이 프로젝트에서 가장 조용한 종류의 버그다.
화면이 "만들 수 있다"고 말한 블록을 서버가 400 으로 거절하면 사용자는 이유를 알 수 없다.

#### 결정

**판정을 `packages/domain` 으로 내리고, 화면과 서버가 같은 함수를 쓴다.**

```
previewWithCandidate(input, candidate)   ← 화면(시트)이 부른다
assertBlockFitsInBudget(result, cand)    ← 서버(createBlock)가 부른다
                └ 둘 다 requestedMinutesOf() 와 같은 비교식을 쓴다
```

`requestedMinutesOf` 를 뽑아내면서 `assertBlockFitsInBudget` 의 분기 하나(그날에 안 걸치면 조기 반환)가
자연히 사라졌다 — 0분은 어차피 어떤 남은 시간보다 크지 않다.

시트는 그래서 `previewWithCandidate` 하나만 부르고, 화면에는 **판정 로직이 한 줄도 없다.**
`isExceeded` 가 두 곳에서 달라질 방법이 구조적으로 없다.

파리티 테스트를 한 개 두었다 — 같은 입력에 대해 `preview.isExceeded` 와
`assertBlockFitsInBudget` 의 throw 여부가 항상 같아야 한다. 이게 깨지면 즉시 빨간불이 켜진다.

#### 값의 이름을 나눈 이유

미리보기에는 서로 다른 두 숫자가 동시에 필요하다.

| 값 | 기준 | 쓰는 곳 |
|---|---|---|
| `requestedMinutes` | **블록 길이** | 예산 검증 — 겹치는 자리에 놓아도 길이만큼 청구한다 (N-026) |
| `remainingAfterMinutes` | **합집합** | 화면의 큰 숫자 — 겹친 1분은 한 번만 센다 |

10:00 캘린더 일정 위에 10:30 블록을 놓으면 `requested=60`, 남는 시간은 90분만 줄어든다.
이 둘을 한 값으로 합치려 하면 반드시 한쪽이 틀린다.

⭐ **초과일 때 `remainingAfterMinutes` 는 음수를 그대로 낸다.** 0 으로 접으면
"얼마나 넘었는지"가 사라져 사용자가 길이를 얼마나 줄여야 할지 알 수 없다.

#### 곁다리로 잡은 버그

**`screen-day.css` 가 `globals.css` 에서 import 되지 않고 있었다** (U-04 부터).
하루 화면이 스타일 없이 렌더링되고 있었다. 파일은 있고 화면 클래스도 붙어 있어서
코드만 읽으면 보이지 않는다 — 빌드 산출 CSS 를 실제로 열어봐야 드러난다.

> 새 화면을 붙일 때는 **번들에 그 CSS 가 실제로 들어갔는지** 한 번 확인한다.
> `curl` 로 페이지의 CSS 링크를 따라가 클래스 이름을 grep 하면 30초면 끝난다.

### N-034 · 집중 화면은 '분기'를 앞에 두고, 타이머는 사진 위에서 흐른다 ⭐

**날짜**: 2026-08-20 · **역할**: 퍼블(20년차 퍼블리셔) + 개발 · **관련 작업**: U-05 · F-01

#### 1. `/focus` 는 화면이 아니라 분기다

집중 탭을 누르면 무엇을 보여줄 것인가. 진행 중인 블록이 없을 때 **빈 타이머 화면**을 띄우면
사용자가 "무엇을" 시작하는지 모른 채 버튼을 누르게 된다.

```
/focus            → 진행 중 블록 있으면 /focus/{id}, 없으면 /day?new=1 (생성 시트가 열린 채)
/focus/{blockId}  → S-04 집중 화면
```

`?new=1` 로 시트를 여는 이유: 시트를 별도 라우트로 만들면 **뒤의 하루 화면이라는 맥락이 사라진다.**
생성 시트의 주 오브젝트가 "오늘 남은 시간"인데, 하루 화면 없이 뜨면 그 숫자가 어디서 왔는지 알 수 없다.

#### 2. 탭 바를 숨기는 건 장식이 아니다

S-04 는 하단 탭을 숨긴다 (화면정의서 §1). `FloatingTabs` 가 `pathname.startsWith('/focus/')` 로 스스로 빠진다.

> 탭을 남겨두면 **실수로 화면을 벗어나 타이머만 도는 상태**가 만들어진다.
> 나가는 길을 좌상단 닫기 하나로 좁히면, 나가는 행위가 "지금 하던 걸 접는다"는 의사 표시가 된다.

#### 3. 타이머 — 서버가 준 '사진' 위에서 흐른다 (F-01)

```
서버 → { focusSeconds: 26, serverTime: '2026-08-20T10:40:52', blockStatus: 'RUNNING' }
화면 → 매 250ms:  26 + floor((지금 − 10:40:52) / 1000)
```

⭐ **누적하지 않는다.** `focusSeconds += 1` 이었다면 탭이 백그라운드로 간 동안 놓친 초가 영영 사라진다.
매 틱마다 처음부터 다시 계산하므로, 틱을 30개 놓쳐도 **돌아온 첫 틱에서 정확한 값**이 나온다.

| 규칙 | 이유 |
|---|---|
| `Date.now()` 대신 `Date.now() + offset` | 사용자 PC 시계가 5분 틀어져 있어도 흡수한다 |
| 오프셋 초기값을 **렌더 중에 계산하지 않는다** | 렌더는 순수해야 한다. 실제로 `react-hooks/purity` 린트가 잡았다 — SSR 과 하이드레이션의 값이 달라진다 |
| `PAUSED` 는 서버 값 고정 | 흐르게 두면 화면의 집중 시간이 원장보다 커진다 |
| `visibilitychange` 에서 서버에 다시 묻는다 | 숨겨진 동안 잰 값은 거짓이다. **데이터를 가져오는 일은 화면이 하고, 훅은 시계만 본다** |
| 타이머 숫자는 `aria-live="off"` | 매초 읽어주면 소음이다. 상태 전이만 `polite` 로 알린다 |

#### 4. 완료 후 화면 — 되돌릴 수 없다고 말한다

정산은 즉시 일어나고 원장은 UPDATE 하지 않는다. 그래서 완료 직후 화면에
`학습에 51분` + **"되돌릴 수 없습니다"** 를 명시한다. 다음 행동은 두 개다 —
`계속 이어서`(→ `/day?new=1`) · `오늘로 돌아가기`(→ `/day`).

시안 C 의 **"구글 캘린더에도 남깁니다" 체크박스는 넣지 않았다.** 쓰기 파이프(B-15)가 Phase 2 로 밀려 있다.
아직 없는 기능을 체크박스로 약속하면, 켜둔 사용자는 캘린더에 아무것도 안 남은 걸 나중에 발견한다.

#### 실경로 검증

로컬 dev + 실 DB. 60분 STUDY 블록을 즉시 시작해 태웠다.

```
/focus/{id}   다이얼 59:49 · 뽀모도로 1/2 · 태그·제목·10:00–11:00 · 하단 탭 없음 ✅
pause         이어서 하기 + "일시 정지됨 · 1번째", 다이얼 59:34 에서 정지 ✅
resume        RUNNING 복귀 (focusSeconds 26 유지) ✅
complete      EARLY_FINISHED 로 정산 ✅
정산 후 /focus/{id}  → 307 /day        (집중할 대상이 없다) ✅
진행 중 없음 /focus  → 307 /day?new=1  (시트가 열린 채로 SSR) ✅
```

검증용 행은 전부 삭제했다.

### N-035 · 마감 직전 최종 동기화는 **실패해도 마감을 막지 않는다** ⭐

**날짜:** 2026-08-20 · **역할:** 개발 (아키텍트) · **관련:** B-09 · B-11 · 정책 §3.2 · §3.4 · N-032

#### 무엇을 정했나

주간 마감(`closeWeek`)의 1단계 최종 동기화를 `syncCalendarWeek` 호출로 연결했다.
N-032 에서 비워둔 자리다. 동시에 **실패 처리 방식을 확정했다.**

| 최종 동기화 결과 | 마감은? | `weekly_closing.calendar_sync_result` |
|---|---|---|
| 성공 | 진행 | `SYNCED` (+ `last_synced_time`) |
| 구글 연동 없음 | 진행 | `NOT_CONNECTED` |
| 토큰 만료 · 구글 장애 · 네트워크 예외 | **그래도 진행** | `FAILED` |

#### 왜 실패해도 닫는가

처음에는 "못 읽었으면 마감을 미루자"가 자연스러워 보였다. 다음 주에 다시 시도하면 되니까.
**틀렸다.** 미루면 두 가지가 같이 나빠진다.

1. **예산이 조용히 좁아진다.** 그 주의 `imported_calendar_event` 행이 살아남고,
   예산 계산기는 그걸 계속 점유자로 센다. 사용자는 이유 없이 "남은 시간"이 줄어든 하루를 본다.
2. **다음 주에도 똑같이 실패한다.** 토큰 만료(N-028)는 저절로 낫지 않는다.
   재로그인 전까지 매주 미루기만 반복하고, 미마감 주가 쌓인다.

그래서 **읽은 데까지로 닫고, 못 읽었다는 사실을 기록한다.**
주중 동기화가 이미 쌓아둔 일정은 그대로 원장에 들어간다 — 잃는 건 "마지막 몇 시간의 변경분"뿐이다.
캘린더를 아예 못 읽었다면 그 주는 0건으로 닫히지만, `FAILED` 라 리포트가 거짓말하지 않는다 (정책 §3.4).

> 이게 주중 내내 쌓아두는 설계(정책 §3.4)의 값을 치르는 지점이다.
> 마감 시점에만 읽는 설계였다면 토큰이 만료된 주는 **통째로 사라졌다.**

#### 왜 예외까지 삼키는가

`syncCalendarWeek` 는 토큰 만료·구글 4xx/5xx 를 `status` 로 돌려주지 관례적으로 throw 하지 않는다.
그래도 `try/catch` 로 감쌌다 — `fetch` 자체가 끊기거나 DB 가 튕기면 예외가 올라오기 때문이다.

여기서 예외가 위로 새면 `runWeeklyClosing` 이 그 회원을 `failedMemberIds` 로 넘기고 **주가 열린 채 남는다.**
그건 위의 1·2 를 그대로 부른다. **구글이 죽은 것과 그 주를 못 닫는 것은 별개의 사고다.**

#### 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 동기화 실패 시 마감 보류 | 위 1·2. 토큰 만료는 저절로 낫지 않는다 |
| 마감 시점에만 캘린더를 읽는다 | 하필 그때 토큰이 만료돼 있으면 그 주가 통째로 사라진다 (정책 §3.4) |
| 실패를 `SYNCED` 로 적고 조용히 넘어간다 | 리포트가 거짓말한다. 사용자는 빈 주를 보고 자기가 논 줄 안다 |
| 재시도 루프를 마감 안에 넣는다 | 마감 배치가 회원 수 × 재시도만큼 길어진다. 다음 주 배치가 따라잡게 두는 편이 낫다 (N-031 과 같은 원칙) |

#### 남은 리스크 (기록만)

`closeWeek` 이 이제 **회원당 구글 호출 1회**를 한다. `runWeeklyClosing` 은 최대 100건을 순차로 돈다.
회원이 늘면 300초 상한에 닿는다. 지금은 회원이 1명이라 문제가 아니고, `hasMore` 로 이어 도는 길도 있다.
**회원 두 자릿수가 되면 `CLOSING_TARGET_LIMIT` 을 먼저 낮춘다** — 병렬화보다 그게 안전하다
(구글 rate limit 과 커넥션 한도를 동시에 건드리지 않는다).

### N-036 · 통합 테스트는 **실 DB 없이** 모듈 경계에서 막는다 ⭐

**날짜:** 2026-08-20 · **역할:** QA (리드) · **관련:** T-03 · 테스트계획 §4 · §5 · §6

#### 무엇을 정했나

배치·동기화 통합 테스트(T-03)를 **`vi.mock` 으로 `../prisma` · 구글 fetch 를 갈아 끼우고** 돌린다.
테스트용 Postgres(Testcontainers·별도 Supabase 프로젝트)를 띄우지 않는다.

`apps/web/src/server/services/{settlement,closing,calendar-sync}.test.ts` — **87건**.

#### 왜

| 이유 | 설명 |
|---|---|
| 실 DB 는 이 프로젝트에서 **비싸다** | Supabase 무료 티어 프로젝트 하나뿐이고, 커넥션 한도가 좁다(풀러 + `connection_limit=1`). CI 가 붙으면 개발용 DB 와 싸운다 |
| Docker 를 전제하지 않는다 | 이 PC 는 사내망이라 이미지 pull 이 막힐 수 있다. **Vercel 도 못 여는 망**에서 Testcontainers 를 전제하면 테스트가 아무 데서도 안 돈다 |
| 잡고 싶은 버그가 **SQL 이 아니다** | 필터 판정이 `exclusion_reason` 까지 도달하는가, 동기화가 일정 조회보다 **먼저** 도는가, 실패해도 마감이 진행되는가 — 전부 **호출 순서와 분기**다. Postgres 가 있어야 보이는 게 아니다 |
| 존 검증이 진짜 목적이다 | §6 은 프로세스 TZ 를 바꿔 돌려야 한다. DB 를 끼우면 실행이 느려져 세 번 돌릴 수 없다 |

#### 대신 무엇을 포기했나 (기록해 둔다)

**SQL 자체는 검증되지 않는다.** UNIQUE 제약·`skipDuplicates`·`groupBy` 는 가짜가 흉내 낸 것이지
Postgres 가 대답한 게 아니다. 이 셋은 **실 DB 로 이미 한 번 태워 확인했다**(B-06·B-08·B-09 세션).
스키마를 바꾸면 그 확인을 다시 해야 한다 — 테스트가 대신해 주지 않는다.

> 즉 이 테스트들은 **회귀 방어**지 최초 검증이 아니다. 그 구분을 흐리면
> "테스트가 통과하니 실 DB 확인은 건너뛰자"가 되고, 그때 조용히 틀린 숫자가 나간다.

#### `pnpm test:tz` — 존을 세 개로 바꿔 돌린다 (#39-b)

```
UTC               Vercel 함수 · GitHub Actions 크론의 실제 환경
Asia/Seoul        개발자 노트북. 여기서만 통과하는 코드가 가장 흔한 사고다
America/New_York  앱 존보다 뒤에 있는 존. 날짜 경계가 반대로 어긋난다
```

`vitest.config.ts` 는 이제 TZ 를 **못 박지 않고** 밖에서 받는다(기본 UTC).
`scripts/test-timezones.mjs` 가 세 번 돌린다 — 셸이 아니라 node 인 이유는
`TZ=... pnpm test` 가 Windows PowerShell 에서 안 먹기 때문이다. 개발은 Windows, CI 는 리눅스다.

⚠️ **테스트 안에서 프로세스 존을 단언하지 않는다.** 실제로 처음엔
`expect(new Date().getTimezoneOffset()).toBe(0)` 을 넣었다가 `test:tz` 에서 그 두 개만 깨졌다.
지켜야 할 성질은 *"UTC 에서 돈다"* 가 아니라 **"존을 바꿔도 답이 같다"** 다. 단언을
`parseAppDate(...).offset === 540`(앱 존은 언제나 KST)으로 바꿨다.

### N-037 · 상태 화면(D-06)에는 **공용 컴포넌트를 만들지 않는다** ⭐

**날짜:** 2026-08-20 · **역할:** 디자인 (프로덕트 디자이너) · **관련:** D-06 · 화면정의서 §0.4 · 디자인시스템 §1.1

산출물: `docs/디자인/시안-G-상태.html` — 7개 상태 (로딩 2 · 비어 있음 2 · 에러 3)

#### 무엇을 정했나

`아이콘 + 제목 + 버튼`을 세로로 쌓은 **`<EmptyState>` 공용 컴포넌트를 만들지 않는다.**
상태 화면도 그 화면의 주 오브젝트(리포트=링, 하루=미터)를 주인공으로 유지한다.

이건 §1.1 의 재확인이다. 1차 시안이 *"세 개 다 똑같은 UI에 색만 다르다"* 로 기각됐는데,
상태 화면에서 공용 컴포넌트를 쓰면 **정확히 그 실수를 뒷문으로 되돌린다.**
빈 화면은 사용자가 이 앱을 처음 만나는 자리라 특히 그렇다 — 링을 지우면 이 화면이 무엇인지 배울 기회를 잃는다.

#### 세 가지 규칙

**1. 로딩은 정상 화면과 같은 형태여야 하고, 빈 상태는 달라도 된다**

로딩 → 정상은 *같은 사실이 도착하는* 것이라 한 픽셀도 움직이면 안 된다.
빈 상태 → 정상은 *다른 사실로 바뀌는* 것이라 레이아웃이 달라도 된다.
이 구분이 없으면 스켈레톤을 대충 그리거나, 빈 상태를 억지로 정상 형태에 끼워 맞추게 된다.

| 스켈레톤 규칙 | 이유 |
|---|---|
| 반지름·높이·여백을 정상과 같게 | 그래야 도착해도 안 움직인다. **이게 스피너를 금지한 진짜 이유다** |
| 폭은 "실제로 올 글자 수"만큼만 | 100% 폭 바를 깔면 도착할 때 확 줄어 오히려 더 튄다 |
| 사각형은 쓸어내리고(sweep), 링은 숨쉰다(breathe) | 링은 사각형이 아니라 쓸어낼 수 없다 |
| 블룸은 절반만 켠다 | 아직 아무 값도 없는데 화면이 뜨거우면 거짓말이다 |
| ⭐ **하루의 격자·시각·지금 선은 덮지 않는다** | 그건 서버가 주는 값이 아니라 **이미 아는 시간**이다. 덮으면 일부러 늦게 보여주는 셈이다 |

**2. 빈 상태는 "없음"이 아니라 "아직"이다**

- 리포트: **62px 로 `0시간 0분` 을 쓰지 않는다.** 히어로 숫자는 성취를 재는 자리다 —
  거기 0 을 크게 박으면 *"아직 시작 전"* 이 *"이미 실패"* 로 읽힌다. 빈 링 + 다음 행동으로 대신한다
- 빈 링에 **짧은 색 조각을 얹지 않는다.** 값이 없는데 카테고리 색을 칠하면 차트가 거짓말을 한다
  (처음엔 "채워질 자리"라는 뜻으로 넣었다가, 화면에서 그냥 떠 있는 파란 점으로 읽혀 뺐다)
- ⭐ **하루의 빈 상태는 나쁜 상태가 아니다.** *남은 시간이 최대인 상태* 다 —
  이 앱에서 가장 좋은 상태를 회색으로 죽이면 안 된다. 숫자를 정상 크기로 살려 둔다
- 제안은 카드가 아니라 **격자 위의 구간**으로 놓는다. "지금부터 3시간"이 형태로 보인다

**3. 에러는 화면을 덮지 않고, 아는 것은 남긴다**

- ⭐ 캘린더를 못 읽어도 **내 블록은 안다.** 미터를 통째로 지우면 아는 것까지 잃는다
- 모르는 구간은 **비움이 아니라 「알 수 없음」으로 칠한다.** `0시간` 과 `모름` 은 다른 사실이다
- 총계는 왔고 분포만 실패했으면 총계를 남긴다. 같이 지우면 사실이 아닌 화면이 된다
- 실패 카드는 **정상 카드의 자리와 높이를 그대로** 차지한다 — 재시도가 성공해도 안 튄다
- 재시도는 문장 속 링크가 아니라 **44px 타겟**이다. 실패한 사람을 두 번 실패시키지 않는다

#### 미연동은 에러가 아니다 (배너 위치를 화면정의서에서 바꿨다)

`NOT_CONNECTED` 에 **경고색을 쓰지 않는다.** 사고가 아니라 제안이다 —
`--warn` 을 칠하면 사용자는 자기가 뭘 잘못한 줄 안다.

⚠️ **화면정의서 S-02 는 이 배너를 "하단"에 두라고 적혀 있다. 시안은 `일정` 세그먼트 바로 아래로 옮겼다.**

| 왜 | |
|---|---|
| 기능 | 하단에 두니 **떠 있는 탭이 33px 을 덮었다.** 목록 몇 줄이 가리는 건 정상이지만(스크롤하면 된다), **행동을 요구하는 배너가 가리는 건 버그다** |
| 의미 | 비활성 `일정` 세그먼트가 질문이고 배너가 답이다. **둘이 떨어져 있으면 아무도 잇지 않는다** |

`일정` 세그먼트는 **숨기지 않고 비활성으로 둔다.** 숨기면 그런 축이 있다는 사실 자체를 모른다.

#### 시안을 그리다 잡은 것 (렌더링해서 확인함)

| 🐛 | |
|---|---|

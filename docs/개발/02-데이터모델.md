# NFS 데이터 모델

| 항목 | 내용 |
|---|---|
| 버전 | **v2.0** (Postgres 전환 · N-022) |
| 최종 갱신 | 2026-08-19 |
| 작성 | 20년차 백엔드 아키텍트 |
| 선행 | `../기획/03-서비스정책.md` |
| 후속 | `03-API명세.md` · `../테스트/01-테스트계획.md` |

> **DB는 Supabase PostgreSQL 15** (N-022). MySQL 8(N-015)은 폐기됐다.
> ORM은 **Prisma 5** — 단일 원천은 `packages/db/prisma/schema.prisma` 다.
>
> ⭐ **아래 테이블·컬럼·제약·인덱스 설계는 DB가 바뀌어도 그대로 유효하다.**
> 아래 표기 대응만 읽고 본문으로 넘어가면 된다.
>
> | 이 문서 표기 | Postgres | Prisma |
> |---|---|---|
> | `BIGINT` PK, AI | `bigserial` | `BigInt @id @default(autoincrement())` |
> | `BIGINT` (일반) | `bigint` | `BigInt` ⚠️ JSON 직렬화 전 `Number()` 변환 |
> | `VARCHAR(n)` | `varchar(n)` | `String @db.VarChar(n)` |
> | `DATETIME` | `timestamp(0)` | `DateTime @db.Timestamp(0)` |
> | `DATE` (날짜만) | `date` | `DateTime @db.Date` ⚠️ **반드시 `@db.Date`** — 안 붙이면 시각부가 섞여 자정 경계가 깨진다 |
> | `UNIQUE (a, b, c)` | — | `@@unique([a, b, c])` |
> | enum 문자열 컬럼 | **네이티브 `enum`** | Prisma `enum` — 값은 `packages/domain/types`와 같은 문자열 |
>
> **MySQL에서 달라진 것 (실무상 전부):**
> 1. **네이티브 enum이 생겼다.** `category_tag` 같은 컬럼을 `VARCHAR(20)` 대신 진짜 enum으로 선언한다. 오타가 DB에서 막힌다.
>    다만 **enum 값 추가는 마이그레이션이 필요**하므로, 값이 자주 늘 컬럼(`exclusion_reason` 등)은 `varchar`로 남긴다.
> 2. **식별자 대소문자.** Postgres는 따옴표 없는 식별자를 소문자로 접는다. raw SQL 별칭에 큰따옴표 필수 (`01-아키텍처.md` §4.1).
> 3. **`SUM(int)`이 `bigint`로 온다.** 응답 직전에 `Number()` 변환. 안 하면 JSON 직렬화에서 터진다.
> 4. **부분 유니크 인덱스를 쓸 수 있다** (`WHERE` 절 있는 UNIQUE). §1.1의 멱등성 키 설계가 더 깔끔해질 여지가 생겼지만, **지금 설계를 바꾸지 않는다** — 단일 문자열 키가 이미 문제없이 동작하고, 두 DB 사이에서 이식성이 높다.

## 1. 설계 원칙 — 가변 작업 영역과 불변 원장의 분리

```
 ┌─ 가변 · 잦은 CUD · 행이 적다 ────────┐        ┌─ 불변 · append-only · 행이 많다 ─┐
 │  active_block                        │  정산  │  time_log                        │
 │  imported_calendar_event             │ ─────▶ │  (가계부 원장)                    │
 └──────────────────────────────────────┘        └──────────────────────────────────┘
                                                  weekly_closing (마감 상태)
```

**왜 나누는가 (N-007)**

| 이득 | 설명 |
|---|---|
| 인덱스 비용 분리 | 통계용 복합 인덱스가 초당 UPDATE 비용을 물지 않는다 |
| 통계 정합성 | 통계 쿼리에 `where status='COMPLETED'` 가 영원히 따라붙는 일이 없다. **존재 자체가 확정의 증거** |
| 스키마 오염 방지 | 진행 중에만 의미 있는 컬럼(`lastResumedTime`)과 완료 후에만 의미 있는 컬럼(`statDate`)이 섞이지 않는다 |
| 장기 운영 | `time_log`는 append-only라 연도별 파티셔닝·아카이빙이 쉽다 |

**대가:** 이관 트랜잭션이 새 실패 지점이 된다 → 1.1 멱등성으로 막는다.

### 1.1 멱등성 (⭐ 반드시)

```sql
UNIQUE (member_id, source_type, source_reference_key)
```

배치 재실행이나 네트워크 재시도로 같은 원본이 두 번 정산되는 것을 **DB가 막는다.**
애플리케이션 검사에만 의존하면 동시 실행 시 뚫린다.

`source_reference_key`는 문자열이다.
- `NFS_BLOCK` → `active_block_id` 를 문자열로
- `GOOGLE_CALENDAR` → 구글 이벤트 id

> 타입이 다른 두 키를 각각 nullable 컬럼 + 부분 유니크로 두는 방식은 제약이 둘로 쪼개지고 조회 조건도 분기된다.
> 숫자 id를 문자열로 담는 게 아름답지는 않지만, **멱등성 제약을 DB 한 줄로 끝낼 수 있는 대가로는 싸다.**
>
> Postgres로 오면서 부분 유니크 인덱스(`WHERE` 절 있는 UNIQUE)를 쓸 수 있게 됐지만 **바꾸지 않는다.**
> 지금 설계가 문제없이 동작하고, DB를 다시 옮겨도 그대로 성립한다.

## 3. 이관 트랜잭션 (⭐ B-06)

### 3.1 ActiveBlock → TimeLog

```
@Transactional
1. 최종 집중 시간 확정   finalFocusSeconds = accumulated + (now − lastResumed)
2. 시작 시각 결정        actualStartTime ?: plannedStartTime
3. 겹침 차감 계산        DailyTimeBudgetCalculator 재사용
4. TimeLog INSERT        (UNIQUE 위반 시 이미 정산됨 → 정상 종료)
5. ActiveBlock DELETE
```

**순서가 중요하다.** INSERT 먼저, DELETE 나중. 중간에 끊기면 원본이 남아 재시도할 수 있고,
재시도해도 UNIQUE가 중복을 막는다. 반대 순서면 기록이 유실된다.

### 3.2 ImportedCalendarEvent → TimeLog (주간 마감)

```
@Transactional (회원 단위)
1. 지난주 구간 최종 1회 동기화
2. excludedFromStatistics = false 인 이벤트만 대상
3. 각 이벤트에 대해 NFS 블록과의 겹침 차감 → 0분이면 스킵
4. TimeLog INSERT (source_type = GOOGLE_CALENDAR)
5. 해당 주 imported_calendar_event DELETE
6. weekly_closing 갱신 (CLOSED + sync_result)
```

## 4. 예산 계산기 (⭐ B-05)

`budget/DailyTimeBudgetCalculator` — **등록 검증과 통계 집계가 같은 것을 쓴다.**

```
입력 : memberId, 대상 날짜
처리 : 1. TimeLog(stat_date=D) + ActiveBlock(work_date=D)
          + ImportedCalendarEvent(해당 구간, 제외 안 됨) 을 [시작,끝) 구간으로 수집
       2. 시작 시각 오름차순 정렬
       3. 인접 구간 병합 (합집합)
       4. 병합된 구간의 총 분 = 점유
결과 : 점유 분, 남은 분(1440 − 점유), 출처별 내역
```

구현 시 **명시적 반복문**으로 쓴다 (CLAUDE.md §3). 겹침 계산은 경계 조건 디버깅이 잦아
중간값을 눈으로 따라갈 수 있어야 한다.

> 계산기가 두 벌이면 하루 화면의 "남은 시간"과 리포트의 합계가 어긋난다.
> 이 프로젝트에서 가장 조용하고 치명적인 버그가 여기서 난다.

## 5. 마이그레이션

**Prisma Migrate.** 단일 원천은 `packages/db/prisma/schema.prisma` 이고,
생성된 SQL은 `packages/db/prisma/migrations/{타임스탬프}_{설명}/migration.sql` 에 **커밋한다.**

| 순서 | 마이그레이션 | 내용 |
|---|---|---|
| 1 | `init_member` | member |
| 2 | `active_block` | active_block |
| 3 | `time_log` | time_log (+ 인덱스 2, **유니크 1** ⭐) |
| 4 | `imported_calendar_event` | imported_calendar_event |
| 5 | `weekly_closing` | weekly_closing |
| 6 | `category_color_mapping` | category_color_mapping |

| 환경 | 명령 | 주의 |
|---|---|---|
| 로컬 | `pnpm prisma migrate dev` | 스키마를 고치면 SQL을 생성해준다 |
| 운영(Supabase) | `pnpm prisma migrate deploy` | ⛔ **운영에서 `migrate dev` 금지** — 드리프트를 감지하면 DB를 리셋한다 |

⚠️ **마이그레이션은 반드시 `DIRECT_URL`(5432 직결)로 돈다.**
런타임용 풀러(6543/pgBouncer)로 시도하면 준비된 구문을 지원하지 않아 실패한다 (`01-아키텍처.md` §7).

**생성된 `migration.sql`을 반드시 눈으로 읽고 커밋한다.**
Prisma는 컬럼 타입 변경을 `DROP` + `ADD`로 만들 때가 있다. 이건 v1.0의 Flyway에는 없던 위험이다 —
Flyway는 사람이 SQL을 쓰기 때문에 자동으로 데이터를 날릴 수 없었다.

> `db push`는 마이그레이션 파일을 남기지 않는다. **이 프로젝트에서는 쓰지 않는다.**
> 원장(`time_log`)의 UNIQUE 제약이 이력 없이 사라지면 이중 정산이 조용히 통과한다.
